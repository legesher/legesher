# Python Builtin: `UserWarning` - Translation Brief (Tier 1)

**Category:** exception
**Type:** exception class (warning category)
**Python Version:** 3.x+
**Difficulty:** MEDIUM

---

## Quick Summary

`UserWarning` is the default warning category: it is what `warnings.warn()` emits when no category is given. It subclasses `Warning` and marks generic warnings generated by user code (as opposed to specialized categories like `DeprecationWarning`). Like all warnings, it is advisory: it is shown by default and execution continues.

---

## Code Examples FIRST (Learn by Seeing)

### Example 1: Minimal Usage

```python
# warn() with no category defaults to UserWarning
import warnings

warnings.warn("this configuration is untested")
print("still running")
# stderr shows: UserWarning: this configuration is untested
```

**What this does:** Calling `warnings.warn()` without a `category` argument emits a `UserWarning`. The message is printed to `stderr` (once per source location, under default filters) and the program continues on the next line - nothing is raised, nothing fails.

### Example 2: Common Pattern

```python
# A library warning its callers about a questionable argument
import warnings

def set_retries(count):
    if count > 10:
        warnings.warn(
            f"retries={count} is unusually high; capping at 10",
            UserWarning,
            stacklevel=2,   # point the warning at the CALLER's line
        )
        count = 10
    return count

set_retries(50)   # warning printed, then execution continues
```

**What this does:** `UserWarning` is the general-purpose category for "your code did something questionable but workable." `stacklevel=2` makes the warning report the caller's line instead of the library's own `warn()` line, which is the conventional courtesy in library code. The function still completes and returns normally.

### Example 3: Edge Case

```python
# Filtering and promoting UserWarning specifically
import warnings

warnings.simplefilter("ignore", UserWarning)
warnings.warn("silenced")                       # nothing printed

warnings.simplefilter("error", UserWarning)
try:
    warnings.warn("now fatal")
except UserWarning as exc:                      # catchable: Warning subclasses Exception
    print(f"caught: {exc}")

# DeprecationWarning is untouched by the filters above -
# filters match by category, and UserWarning is just one category
```

**What this shows:** Filters target `UserWarning` without affecting sibling categories. Because `UserWarning` inherits from `Warning` (which inherits from `Exception`), an `"error"` filter turns the advisory message into a real raised exception. The category name is the handle users grab to control exactly this kind of warning.

4. `SyntaxWarning` - Sibling category for dubious syntax

**Pattern rule:** All warning categories are compound nouns: qualifier + the shared "warning" root. `UserWarning` = "user" + "warning," where "user" means the user of Python (the programmer / user code), attached per the target language's noun-compounding rules.

## Etymology (Brief)

**English Origin:** Compound (Latin-derived + Germanic)

**Root meaning:** "User" comes from Latin "usus" (use); in computing it denotes the person or code employing a system. "Warning" comes from Old English "warnian," to caution. Together: a caution originating from user-level code.

**Why Python uses this:** The warning system needed a default, general-purpose category for warnings that don't fit a specialized bucket (deprecation, syntax, runtime, ...). "User" distinguishes warnings written by users of Python - application and library authors calling `warnings.warn()` - from warnings the interpreter itself generates about language-level issues.

## Concept Explanation (Intermediate Level)

**What it does:**

`UserWarning` is the workhorse category of the warning system. Whenever code calls `warnings.warn("message")` without naming a category, Python wraps the message in a `UserWarning`. It signals "generic caution from user code": a suspicious argument, a fallback being taken, a configuration that will work but probably isn't what the caller intended.

The word "user" here means the *user of Python* - the programmer whose code emits the warning - not the end user sitting at a screen. This matters because the warning hierarchy encodes audience elsewhere too: `DeprecationWarning` targets developers, `FutureWarning` targets end users of applications. `UserWarning` is simply "user code's generic warning" with no specialized meaning attached.

Under default filters `UserWarning` is shown (once per source location) and execution continues. Consumers can silence it (`simplefilter("ignore", UserWarning)`), show every occurrence, or promote it to an exception, all without touching other categories. Library authors who find themselves emitting many `UserWarning`s for one recurring theme usually graduate to a custom `Warning` subclass so their users can filter precisely.

**Key behaviors:**

1. **Default category of `warnings.warn()`:** `warnings.warn("msg")` is equivalent to `warnings.warn("msg", UserWarning)`. This makes `UserWarning` the most commonly seen category in practice.

2. **Shown by default:** `UserWarning` appears in no entry of the default filter list, so it falls through to the `"default"` action - printed once per unique source location, and execution always continues.

3. **Generic by design:** It carries no specialized semantics. When a more specific built-in category fits (deprecation, runtime, syntax, ...), that category should be used instead; `UserWarning` is the fallback.

## Linguistic Form Recommendation

### Part of Speech

**In Python context:**

- **Grammatical role:** Compound noun (qualifier "user" + root "warning")
- **Action vs State:** STATE - names a category of advisory message
- **Temporal aspect:** Instantaneous - emitted at the moment `warn()` runs

### Recommended Form

**Primary recommendation:** Reuse the exact root chosen for `Warning` and attach the standard local word for "user" (the same word used for computer users generally, e.g., in "user interface"). Follow the same compounding pattern the language uses for its "...Error" exception family.

**Forms to AVOID:**

- ❌ A different root than `Warning`'s translation - breaks the family
- ❌ Words implying "end user"/"customer" specifically - here "user" means user code / the programmer
- ❌ Any error/failure word - a `UserWarning` is advisory, the program continues

## Cross-References (Consistency Requirements)

### Terms that MUST align linguistically

**If translating `UserWarning`, check these translations:**

- [ ] `Warning` - the root of this compound must match it exactly
- [ ] `DeprecationWarning` - sibling category; same root, different qualifier
- [ ] `RuntimeWarning` / `SyntaxWarning` - sibling categories; same structural pattern
- [ ] `input` / user-facing terms - whatever word your language pack uses for "user" elsewhere should match

**Consistency rule:**

All twelve warning categories share one "warning" root; only the qualifier changes. Whatever renders `Warning` must reappear unchanged inside `UserWarning`, `DeprecationWarning`, and the rest - one root, twelve compounds.


### Functional relationships

**This term works WITH:**

1. **`warnings.warn()` + `UserWarning`**: the implicit default category

```python
warnings.warn("msg")  # same as warnings.warn("msg", UserWarning)
```

2. **Filters + `UserWarning`**: category-targeted control

```python
warnings.simplefilter("ignore", UserWarning)
```

**Common pairing:**

```python
import warnings

def parse(data, strict=None):
    if strict is None:
        warnings.warn(
            "strict not specified; defaulting to strict=False",
            UserWarning,
            stacklevel=2,
        )
        strict = False
    return data if strict else data.strip()

# Caller decides how much to care:
warnings.simplefilter("ignore", UserWarning)   # silence
parse("  x  ")

with warnings.catch_warnings():
    warnings.simplefilter("error", UserWarning)  # promote inside this block
    try:
        parse("  x  ")
    except UserWarning:
        print("strictness must be explicit here")
```
